# ADR-0001: Run untrusted SQL on a read-only SQLite connection

## Status
Accepted

## Date
2026-10-27

## Context
The app executes SQL from two untrusted sources: text typed by the user and
queries generated by a language model (which can be steered by prompt
injection hidden in the data or the question). A bad query must not be able
to modify or delete data, read other files, or hang the app.

The previous implementation ran every query on a normal read-write
connection. A keyword blocklist existed but was unused, and it would have
rejected legitimate columns such as `last_updated` while missing writes
hidden inside a `WITH ... DELETE` statement.

## Decision
Keep the active dataset in a temporary SQLite file and run queries on a
separate connection opened with `mode=ro` and `PRAGMA query_only = ON`.
SQLite itself refuses any write. On top of that:

- a cheap prefix check (`SELECT`/`WITH`) gives a clear error message;
- Python's `sqlite3` refuses multiple statements in one call;
- results are capped (`QUERY_ROW_LIMIT`), and a progress handler interrupts
  queries that exceed `QUERY_TIMEOUT_SECONDS`;
- on Python 3.12+, `SQLITE_DBCONFIG_DQS_DML` is switched off, so a misspelled
  double-quoted column is a "no such column" error instead of being read as
  a string literal.

## Alternatives considered

### Keyword blocklist only
- Rejected: easy to bypass and produces false positives on column names.

### Parse and validate the SQL with a parser (e.g. sqlglot)
- Pros: can reject statement types precisely.
- Cons: a new dependency, and a parser bug becomes a security bug.
- Rejected: the database engine enforcing read-only is a stronger guarantee
  for less code.

### DuckDB querying the DataFrame in memory
- Pros: faster analytics, no copy into SQLite.
- Cons: read-only enforcement for in-memory data is less direct; another
  heavy dependency.
- Rejected for now; worth revisiting if datasets regularly exceed ~1M rows.

## Consequences
- Every dataset change is copied into SQLite (about 4 s per million rows,
  see the README's performance table).
- The SQL dialect users and the LLM must write is SQLite's.
- Writes are impossible by construction, which is covered by tests in
  `tests/test_storage.py`.
